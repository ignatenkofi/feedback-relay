# feedback-relay — архитектура и требования

Единый приём фидбека для всех проектов: страница → CF Worker (multi-tenant
relay) → Slack (карантин/триаж) → Claude Routine → GitHub issues.

Вынесен из `unevie/feedback-worker` (кнопка «Оставить отзыв» в книге «ЖИЗНЬ»):
схема доказала себя, механизм обобщён в подключаемый инструмент.

## 1. Архитектура

```
┌─ проект A (unevie) ──────┐
│ свой UI → sdk.send()     │──┐
└──────────────────────────┘  │   ┌───────────────────────────┐      ┌────────────────────┐
┌─ проект B (docshelf…) ───┐  ├──▶│ feedback-relay (CF Worker)│─────▶│ Slack: #A-feedback │
│ готовая форма из SDK     │──┘   │ multi-tenant, stateless   │      │        #B-feedback │
└──────────────────────────┘      │ origin/санитизация/лимиты │      └─────────┬──────────┘
                                  └───────────────────────────┘                │ Slack MCP
                                        секрет: SLACK_BOT_TOKEN          ┌─────▼──────────────┐
                                        конфиг: projects.json            │ Claude Routine     │
                                                                         │ триаж-свип         │──▶ GitHub issues
                                                                         │ ✅-реакция = state │    (GitHub MCP)
                                                                         └────────────────────┘
```

| Компонент | Роль | Где |
|---|---|---|
| relay | multi-tenant CF Worker: валидация → Slack | `worker/` |
| SDK | headless-ядро `send()` (+готовая форма, M3) | `sdk/` |
| триаж | Routine-свип Slack → GitHub, ✅-протокол | `triage/ROUTINE.md` |

## 2. Принятые решения (2026-07-12, интерактивно с владельцем)

1. **Тенантность — один multi-tenant воркер.** Реестр `projects.json`
   (id → origins, канал, репо, лимиты); новый проект = запись в конфиге +
   сниппет, без нового деплоя-копии. Альтернатива «воркер-на-проект»
   отклонена: фиксы защиты пришлось бы раскатывать по копиям (боль
   accretion-модели, знакомая по sqst).
2. **Slack-доставка — bot token (`chat.postMessage`)**, не incoming webhooks:
   один секрет на все проекты, пермалинки, message **metadata**
   (`feedback_v1`) как машиночитаемый маркер, `conversations.replies` для
   свипа — вебхукам это недоступно, а токен свипу нужен в любом случае.
3. **Триаж — Claude Routine свип** (Slack MCP + GitHub MCP), не
   reaction-driven Slack App и не прямое создание issues: ноль новой
   инфраструктуры, человеческое качество группировки/классификации,
   спам не долетает до GitHub. Reaction-driven вариант остаётся возможным
   апгрейдом, если захочется мгновенности.
4. **SDK — headless-ядро + опциональная готовая форма.** unevie сохраняет
   свой стилизованный диалог и зовёт только ядро; проекты без своего UI
   берут форму из коробки (M3).

## 3. Принципы

1. **Stateless relay.** Воркер ничего не хранит — «инбокс» фидбека живёт в
   Slack. Ни KV, ни БД, ни буферизации: не копим чужой текст у себя.
2. **Slack = карантин, GitHub = чистовик.** В issue-трекер попадает только
   осмысленный, дедуплицированный фидбек после триажа.
3. **Подключение без кода в relay:** запись в конфиге + сниппет, ≤15 минут
   (чеклист — `worker/README.md`).
4. **PII-минимум.** Пересылается только то, что пользователь написал сам, +
   контекст, который проект явно собрал. IP — только ключ rate limit, не
   попадает ни в Slack, ни в issue. Имя автора не переносится в GitHub.
5. **Разделение кредов.** У воркера — только Slack-токен; GitHub-креды
   существуют только на стороне Routine (MCP), в CF их нет вообще.

## 4. API-контракт (v1)

```
POST /v1/f/{projectId}          Content-Type: application/json
{ "text": string,               // required, ≤4000 символов
  "name": string?,              // ≤80 символов
  "context": {k:v}?,            // ≤20 ключей, k≤40, v≤600 символов
  "sdk": string? }              // версия SDK (диагностика)
// Пофилдовые лимиты — в символах. Всё тело — ≤96 КБ в UTF-8-байтах (DoS-guard,
// `MAX_BODY`): порог с запасом покрывает сумму пофилдовых максимумов даже в
// кириллице/эмодзи (2–4 байта/символ), поэтому формально валидный payload не
// ловит 413 из-за алфавита (#21). Бюджет собранного Slack-сообщения — MAX_MSG.
→ 200 {ok:true}
→ 400 empty|bad_json · 403 origin · 404 unknown_project (и на кривой путь —
  реестр не раскрываем) · 405 method · 413 too_long · 429 rate ·
  500 not_configured · 502 relay_failed|slack_*
```

Версия в пути (`/v1/`): URL вшивается в офлайн-артефакты и должен жить
годами; ломающие изменения — только новым префиксом.

## 5. Конфиг-модель

`worker/projects.json`, проекты добавляются PR'ом (история + ревью):

```jsonc
"unevie": {
  "origins": ["unevie.pages.dev", "*.unevie.pages.dev", "null"], // null = офлайн file://
  "channel": "C0…",              // Slack channel ID, бот приглашён
  "repo":    "ignatenkofi/unevie",  // куда триаж создаёт issues
  "title":   "ЖИЗНЬ", "emoji": "📖",
  "rate":    { "perMin": 6 }     // best-effort ужатие в пределах изолята;
                                 // ≤ кросс-изолятного потолка binding (wrangler.toml)
}
```

Секреты: только `SLACK_BOT_TOKEN` (wrangler secret). Ротация — `secret put`
заново, проекты не передеплоиваются.

## 6. Slack-формат

`chat.postMessage` в канал проекта:

- текст: `{emoji} *{title} — отзыв* · от *{name}*` → цитата `>>>` → контекст
  списком `• *ключ:* значение`;
- **metadata** `event_type: feedback_v1`, `event_payload: {project, sdk}` —
  свип отличает фидбек от людской болтовни в канале без парсинга текста;
- обсуждение/уточнения — в треде сообщения;
- санитизация до отправки: `&<>` экранированы, управляющие символы и переводы
  строк выброшены из имени/контекста — mrkdwn и @-упоминания не подделать.

## 7. Триаж (полный протокол — `triage/ROUTINE.md`)

Ежедневная CCR Routine: непомеченные `feedback_v1`-сообщения → треды →
группировка → классификация (баг/предложение/впечатление/спам) → дедуп по
пермалинку и ключевым словам → issue (`[feedback] <суть>`, labels, цитата +
контекст-таблица + пермалинк треда) → ✅/🚫/❓-реакции. Идемпотентность
двойная: реакции (state в Slack) + поиск пермалинка в issues. Спорное — не
решать: ❓ и краткая сводка владельцу. Пилот: первые свипы показывают
черновики, автосоздание — после калибровки.

## 8. Требования

**Функциональные:** мультипроектность по конфигу · защита unevie-уровня как
базовая, per-project переопределения · `Origin: null` — per-project опция
(офлайн-артефакты) · SDK: send с таймаутом и кодами ошибок; mount (M3):
форма без зависимостей, ≤10 КБ, light/dark · честный ответ пользователю
«отправлено / не отправлено».

**Безопасность:** rate limit — кросс-изолятный binding `project:ip` как
**фиксированный потолок** (сейчас 6/мин для всех проектов, `wrangler.toml`) +
`rate.perMin` как **best-effort** ужатие в пределах изолята (может опустить
эффективный лимит ниже потолка, поднять выше — нет; кросс-изолятно после рецикла
изолята дрейфует к потолку). Ключ `project:ip` — один проект не съедает лимиты
остальных. `perMin` больше потолка binding отклоняет CI (#22). Реальная
per-tier-квота (несколько namespace) — при необходимости, отдельным шагом ·
санитизация до Slack-разметки; экранирование GitHub-markdown — на стороне
Routine · 404 на неизвестный projectId · секрет-ротация без редеплоя
проектов · воркер не логирует тела запросов.

**Нефункциональные:** CF free tier достаточно (единицы сообщений в день;
100k req/день лимит не близко) · Slack недоступен → один внутризапросный
ретрай на 429/5xx, затем 502 клиенту; ничего не буферизуем (осознанно) · диагностика — `wrangler tail` · тесты чистых
функций защиты — `node --test`, интеграционные (miniflare) — M1.

**Совместимость:** старый эндпоинт `unevie-feedback.….workers.dev` живёт как
прокси/как есть — URL вшит в розданные офлайн-файлы, ломать нельзя.

## 9. Этапы

| Этап | Содержимое | Готовность |
|---|---|---|
| **M1** | multi-tenant worker + headless SDK; unevie переезжает (`FEEDBACK_URL` → новый), старый воркер — прокси; miniflare-тесты | скелет в этом репо; деплой + миграция — issue #1 |
| **M2** | Routine-свип по `triage/ROUTINE.md`: пилот с черновиками → автосоздание | issue #2 |
| **M3** | готовая форма-оверлей `FeedbackRelay.mount()` | issue #3 |
| **M4** | подключение следующих проектов (docshelf-полки, будущие) | issue #4 |

**Открытые мелочи:** кастомный домен vs `workers.dev`; e-mail-фолбэк как
второй синк (не делаем, пока не понадобится).
